# DEC-084 補充規範｜Model × Effort 最低足夠配置＋雙向停手

> 日期：2026-10-25
> 性質：`PROJECT_RULES.md` 第 18 節／DEC-084 的規範性補充。
> 原則：**選擇能可靠完成「下一完整工作階段」的最低足夠模型＋最低足夠投入程度；不得固定預設某一模型或某一投入程度。**
> 模型版本：**不得在治理規則寫死版本號**；以客戶當下介面實際可選的 Haiku／Sonnet／Opus／Fable 對應最新版本為準。

## 1. Model × Effort 節省矩陣

| 下一完整工作階段 | 建議模型 | 建議投入程度 |
|---|---|---|
| GitHub 狀態確認、讀 PROJECT_RULES／HANDOFF、機械性文件同步、改字、簡單 commit／merge／PR 收尾 | Haiku | 低 |
| 明確規格的小文件修改、單純 wireframe 落盤、低風險測試調整 | Haiku | 低～中 |
| 一般 UI、一般 coding、單模組 bug、tests、普通 wiring | Sonnet | 中 |
| Wireframe／UX、跨 2～3 模組且規格清楚 | Sonnet | 中 |
| OAuth／Google Sheet 接線、一般跨模組整合、規格清楚的架構判斷 | **先 Sonnet** | 中 |
| 複雜資安、資料契約、投資核心語意、Risk Cap、PIT／look-ahead、重大架構衝突 | Opus | 中～高 |
| 極端複雜、多方案高度衝突、非常大型 migration、重大紅隊；且 Opus 明顯不足 | Fable | 高～更高 |
| Ultracode | **不得預設** | 只有確認該工作確實需要時才建議 |

### 判斷原則

1. **模型與投入程度是兩個獨立軸**，都要判斷。
2. **Haiku 是機械／低風險工作的優先起點；Sonnet 是一般開發主力；Opus 只用在真正高風險／高推理工作；Fable 原則上不用，除非 Opus 明顯不足。**
3. 不得固定 Opus 作日常預設，也不得把 Sonnet＋中寫成所有工作的硬性預設；GitHub Gate、文件同步、PR 收尾等若 Haiku＋低已可靠足夠，就採 Haiku＋低。
4. OAuth／Google Sheet／一般跨模組工作**不得因「跨模組」三字就自動升 Opus**。若規格明確、資料契約未變、沒有高風險資安／不可逆寫入／核心投資語意，先以 Sonnet＋中完成。
5. 若工作途中證明 Sonnet 推理不足，或進入複雜資安、資料契約、重大架構衝突、投資核心語意，再於最近安全停點依第 2 節停手，請客戶切至 Opus。
6. 若兩個模型都能可靠完成，優先採用較低能力／較省額度者；但不得為省額度犧牲 correctness。
7. 客戶介面當下實際可選的模型／投入程度為事實來源。不得因治理文件中的舊版本名稱而要求不存在的版本。
8. 若介面另有「超高／最高／Ultracode」等投入選項，只在 High 明顯不足、且工作確實需要時才提出；**不得因為選項存在就預設使用**。
9. Fable／超高以上不得拿來做日常 GitHub／文件／一般 UI／一般 coding。

## 2. 雙向切換：任何變更都必須停手等待

在每個完整工作階段邊界做一次 Model／Effort Check：

- **目前模型＝建議模型，且目前投入程度＝建議投入程度** → 維持 Silent Autonomous Cruise，直接繼續，不回報 Check 結果。
- **任一項不同** → 到最近安全停點後**立即停手**，不得開始下一完整階段。

此規則不分方向，全部適用：

- Haiku → Sonnet／Opus／Fable：停手。
- Opus／Fable → Sonnet／Haiku：停手。
- 低 → 中／高／超高／最高：停手。
- 高／超高／最高 → 中／低：停手。
- 模型不變、只改投入程度：停手。
- 投入程度不變、只改模型：停手。
- 模型與投入程度同時改：停手。

停手後：

1. 告知客戶「下一階段、目前模型、建議模型、目前投入程度、建議投入程度、原因」。
2. **不得自行假設客戶已切換。**
3. **不得繼續下一完整階段。**
4. 等客戶手動修改設定。
5. 客戶明確回覆「改好了」後才可繼續。
6. 若客戶只改了其中一項，而另一項仍與建議不同，維持停手。

固定格式：

```text
⏸️ 建議切換模型／投入程度，已停手
下一階段：___
目前模型：___
建議模型：___
目前投入程度：___
建議投入程度：___
原因：___
請修改完成後回覆「改好了」。
```

## 3. 只在完整階段邊界重評，避免反而浪費 token

至少在以下時點重評：

1. 新 Batch／下一完整工作階段開始前。
2. 客戶完成 Decision Gate 裁示、正式施工前。
3. 一個高風險子批完成，準備進入不同性質的下一階段時。
4. 工作風險／複雜度實質改變，且已到 Safe Checkpoint 時。
5. 實作／驗證完成，準備轉為單純文件／收尾工作時。

以下**不是**新的完整階段，不應因此頻繁切換：

- 等 CI／workflow。
- 等 QA／audit。
- commit／push。
- PR 開啟。
- 同一不可分割原子工作內的小步驟。
- 同一修復流程中的短暫狀態。

不得為了省一點模型額度，把一個完整 Batch 人為切成大量小段，導致反覆重讀 context、增加 token 消耗。**節省原則是降低不必要的模型／投入程度，不是增加切換次數。**

## 4. 與既有治理的關係

- 本補充與 `PROJECT_RULES.md` 第 18 節共同構成 DEC-084 的現行執行規則。
- **部分取代 DEC-073** 中「目前能力高於所需時，可以不提醒降級並保持靜默直接工作」的方向：自 DEC-084 起，只要下一完整階段的建議模型或投入程度不同，無論升級或降級都必須停手等待客戶修改。
- **加嚴 DEC-059／DEC-061**：由「雙向提醒」提升為「雙向停手＋等待客戶改好」。
- **DEC-014 續有效**：客戶回覆「改好了」後直接繼續，不重新摘要、不重問、不重做。
- `PROJECT_RULES.md` 第 17 節 Minimum Sufficient Effort／Test Scope 續有效；本補充不降低 Risk Cap、投資語意、PIT、資料有效性等高風險工作的 QA 要求。
- Silent Autonomous Cruise 續有效；**Model／Effort 需要切換是正式例外**。

## 5. 客戶裁示來源

客戶 2026-10-25 明確要求：

> 「更換時候都需要等我修改好才能繼續，不管是換低到高或是高到底都需要等我修改」

並再次確認：

> 「可以都停下來等我改完再繼續嗎？ 我不想浪費token」

其後客戶以 Anthropic 官方定價資料再次收斂省量策略，確認：

> Haiku 當機械／低風險工作的優先起點；Sonnet 當主要開發模型；OAuth／Google Sheet／一般跨模組先 Sonnet＋中；Opus 只處理真正高風險／高推理工作；Fable 原則上不用，除非 Opus 明顯不足；Effort 一律採最低足夠值。
