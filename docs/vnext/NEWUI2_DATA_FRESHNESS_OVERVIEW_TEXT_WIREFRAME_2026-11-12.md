## 0. 一頁摘要（給非工程讀者）

**客戶要的**：在 🗂 資料頁放一個「資料新鮮度總覽」，讓人一眼知道：哪些資料是最新的、哪些過期、哪些抓不到、哪些根本還沒接上。

**先講三個現況事實（FACT）**
1. 🗂 資料頁今天是**固定的空殼**，不讀任何資料（全是「⬜ 尚未提供」）。
2. 新版畫面（UI2）目前只有**兩項**資料「接上」：台股加權指數（卡片＋日 K）、市場位階（而且在 UI2 獨立 session 目前恆為「⬜ 尚未載入」，部署端 NOT VERIFIED）。其餘資料（外資、融資、板塊、PMI…）在資料層有檔案，但畫面**還沒接**，接線要先過客戶的 Gate。
3. 台股資料日卡在 **2026-11-09**，是因為較新的資料還在**尚未合併的資料分支**上（INFERENCE，信心高；詳見 §1.7）。畫面本身**無從得知這個原因**，所以任何方案都**不能**在畫面上宣稱原因，也不替客戶決定要不要合併。

**三個方案（差異在「第一眼看到什麼」）**

| 方案 | 一句話 | 手機首屏 |
|---|---|---|
| **A 極簡一張卡＋展開** | 一張總覽卡，只給「幾項、幾項接上、已接上的幾項是什麼狀態」，其餘全部展開才看 | 最輕（估約 10 行） |
| **B 依資料集分列表格** | 每個資料集一列（狀態、接線、資料日、距今天數），固定順序，不重排 | 中～長（8 列，需捲動） |
| **C 異常優先清單** | 先列「需要注意」的項目（依資料狀態排序），正常與未接入收合 | 隨內容變動 |

**AI 推薦（RECOMMENDATION，非裁示）：A。** 理由：目前真的有資料的只有 1～2 項，A 不會把大量「尚未接線」鋪滿畫面，新增欄位最少、最容易撤回；展開層可沿用 B 的列格式，等接線 Gate 逐項放行後自然長成 B。**不推薦 C 作為第一版**：C 在多數項目尚未接線時會顯示「沒有需要注意」，容易被誤讀成「都沒事」，違反「未評估不等於安全」。

**要客戶回的**：選案（A／B／C／A首屏＋B展開層）＋確認「固定清單」內容（§1.2 的 8 項）。格式見 §7。沉默不等於同意，沒回的項目維持 HOLD。

### 0.1 術語表

| 詞 | 白話 |
|---|---|
| 資料日（observation_date） | 這筆資料「屬於哪一天／哪個月」，例如 2026-11-09 收盤 |
| 抓取時間（fetched_at） | 我們的系統「抓到它的時間」，**不等於**資料日 |
| 發布時間（published_at） | 來源官方「公布它的時間」。本系統目前**沒有儲存**這個欄位 |
| 新鮮度（freshness） | 資料日距今有多久、有沒有超過規則；**不等於**資料正確 |
| 過期（Stale） | 有資料，但資料日超過規則容忍範圍 |
| 資料未備（Missing） | 應該有、這次沒拿到（或來源尚未發布） |
| 來源不可用（Unavailable） | 來源真的出錯（紅色）；不是「還沒載入」 |
| 尚未評估（Not Evaluated） | 規則或計算還沒執行；**不等於安全** |
| 尚未接線（Capability） | 這個資料集畫面還沒接上；**不是**資料狀態，也不算失敗 |
| 覆蓋（Coverage） | 預期要有的項目裡，實際拿到幾個 |
| PIT（Point-in-Time） | 資料「當時真的拿得到」；不能用事後才知道的資料解釋當時 |
| 授權（License） | 來源條款是否允許我們這樣呈現與再散布；AI 不下法律結論 |
| Gate | 必須由客戶放行才能往下走的停點 |
| L1 字樣 | 畫面上固定使用的狀態文字（`shared/ui2_contract/text.py`） |

### 1.3 三種時間：實際有哪些（不得捏造）

| 時間 | 資料層現況 | UI2 事實物件是否攜帶 |
|---|---|---|
| **資料日 observation_date** | 各 parquet 有 `date`；`data_cache/metadata.json` 每個 dataset 有 `last_updated`（資料日）；板塊 `metadata.json` 有 `last_updated` | **台股卡／日 K 有**（`as_of`）；其餘 **無**。位階無資料日 |
| **抓取時間 fetched_at** | 各 parquet 有列級 `fetched_at`；`macro_last_good/tw_pmi.json` 有 `fetched_at`／`cached_at` | **值不攜帶**：`TwiiFact`／`TwiiKbarFact` 無此欄，三個 UI2 目錄對小寫 `fetched_at` 識別字命中 0。**但台股日 K 在 L0 `shared/twii_ohlc_contract.py` 內部用它判斷「最近一根是否已收盤完成」（台北 17:00 後）**，不合格時 UI2 只顯示固定人話句「無法確認最近的日 K 已收盤完成」（對應 `FETCHED_AT_MISSING`／`INCOMPLETE_BAR`）。即：它是**有效性輸入**，不只是顯示用 metadata |
| **發布時間 published_at** | **無任何欄位**；資料發布腳本一律寫「n/a（來源未提供）」（`scripts/publish_data_pr.py`） | **無** |

三個必須寫進畫面說明的陷阱：
1. `data_cache/metadata.json` 頂層 `updated_at` 是 **cron 執行時刻**，**不是資料日**；板塊 reader 已明文禁止以它頂替觀測日（`src/data/sector_flow/reader.py::_compute_staleness`）。任何方案都不得拿它當資料日。
2. 列級 `fetched_at` 是「**該列首次寫入**」時間，補值不更新：台股 11-10 那列成交量隔天才補、`fetched_at` 沒變（稽核複驗 §6.2，**文件記載，本文未重驗**）。所以「抓取時間」若要顯示，標籤必須讓人知道它不代表最後修改時間。
3. `metadata.json` 的 `last_error` 非空**不等於真失敗**：`finmind_m1m2` 的 `last_error`＝「抓取結果為空」，配 `fetch_outcome`＝NO_NEW_DATA；`tw_pmi` 配 UNDETERMINED。三態判定唯一入口是 `shared/upstream_state.py::classify_upstream`，畫面文案已有常數（`UPSTREAM_TEXT_FETCH_FAILED`／`UPSTREAM_TEXT_NO_NEW_DATA`／`UPSTREAM_TEXT_UNDETERMINED`）。**NO_NEW_DATA 不重設資料日、不代表資料最新。**

**PMI 的特殊映射（須客戶拍板，C-13）**：現行 `compute_cache_staleness` 對 PMI 回「過期」，原因其實是「頻率沒登記」。若照搬會顯示 `◷ 可能過期`，但這不是「確認資料日過舊」。本線框**不自行決定**映射，展開層固定附帶原因句；選項：照現行（`◷ 可能過期`＋原因）／視為 `⬜ 尚未評估`（規則未登記）。AI 推薦前者並附原因（保持與程式一致、不新增解讀），但屬 RECOMMENDATION。

### 2.2 本頁固定不做的事

不排序成「投資嚴重度」；不計算「資料健康分數」或單一綠燈；不顯示「全部正常」之類總結句；不放刷新／重跑／合併／匯出按鈕（第二期，且須先過 Gate）；不寫原因推論（§1.7）；不對「尚未接線」項目寫「正常」。

### 2.3 計數行的分母規則

- 接線軸分母＝**固定清單項數 N**（§1.2，客戶核准的清單，**不是**即時掃描、不是 `DATA_REGISTRY` 的 78 筆）。

## 5. 方案 C：異常優先清單

**設計意圖**：首屏先回答「有什麼需要注意」；正常與未接線的收合。排序**只依資料狀態**（已知、固定、可解釋），不是投資嚴重度。

### 5.1 排序規則（候選，C-10，須客戶拍板）

分層順序：`⛔ 來源不可用` → `◷ 可能過期` → `◇ 資料未備` → `⬜ 尚未評估`；同層內依固定清單順序。**這是顯示順序，不代表風險大小**（資料頁提案 §4：「依原狀態，不亂排行為嚴重度」）。**尚未接線不是異常**，不進「需要注意」，改以常駐計數行呈現。

### 5.2 八點內容

1. **資料集與來源**：「需要注意」區每項帶來源一句；其餘兩個收合區（正常〈a〉項、尚未接線〈N−K〉項）展開才列。
2. **三種時間**：異常項顯示資料日＋距今；L2 同 B（抓取時間、發布時間）；僅異常項有 L2。
3. **新鮮度判定與閾值**：異常項附一行「判定規則」＋「為什麼被列為過期」（例：頻率未登記／超過日曆日 7 天）。
4. **覆蓋／完整性**：只在異常項內附覆蓋（例：板塊覆蓋不足時）。
5. **PIT／授權**：頁尾一行收合，同 A／B。
6. **缺值／不可用／未評估**：同 §2.1。**空狀態文案是本案最關鍵的一句**：「目前沒有需要注意的已接入項目。尚未接線的 〈N−K〉 項沒有被檢查，不代表它們正常。」常駐顯示，不得省略。
7. **更新或發布異常**：只有當 `is_stale` 為真或上游為 FETCH_FAILED 時才進清單。**弱點（INFERENCE）**：2026-11-12 台股資料日落後 3 天但**未過期**，所以不會出現在「需要注意」——正好是 §1.7 的情境；使用者要展開「正常」區才看得到「距今 3 天」。若客戶希望資料日落後本身就被看見，C 需另加「資料日落後」門檻（＝新閾值，N-1 範圍，須客戶裁示），本線框不新增。
8. **手機首屏密度**：新增 **2 個元件**（異常卡＋計數行）；首屏列數隨異常數變動（估 8～14 行，未量測）；**無異常時最短，但最需要防誤讀**。

## 7. RECOMMENDATION（AI 推薦，**非裁示**）與客戶一鍵回覆格式

### 7.1 推薦

**推薦 A，展開層格式沿用 B。**

理由（皆可驗證）：
1. **目前能誠實顯示的真值只有 2 項**（§2.4）。B 會把 6 列「尚未接線」鋪滿畫面，C 會顯示「需要注意」近乎空白；A 只用一張卡就能同時交代「接上 2 項、其餘 6 項沒被檢查」。
2. **新增項最少、最易撤回**（§6），符合 `CLAUDE.md` §8.1 step 6「自評過度設計」與「最小破壞」原則。
3. **不會成為契約負擔**：A 的明細展開層沿用 B 的列格式，等 `I1144-WIRING-GATE` 逐項放行後，展開層自然成長為 B，**不需重做首屏**。
4. **不推薦 C 作第一版**：C 引入「排序語意」這個新規格（C-10），且在多數項目未接線時，「需要注意」為空的畫面最容易被誤讀為安全（違反「未評估不等於安全」）。若日後多數項目已接線，C 可再作為篩選視圖重新提案。

**推薦的取捨風險（誠實揭露）**：A 把明細藏在展開後，若使用者不展開，只會看到計數；因此計數行必須**永遠**同時顯示「已接入／尚未接線」與五態計數（含 0），這是推薦 A 的前提條件。
